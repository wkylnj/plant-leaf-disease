# 项目实施步骤（可执行版）

> 本文是"怎么做"的施工顺序，与 `方案.md`（"做什么实验、为什么"）分工不同。
> 两者冲突时以本文为准 —— `方案.md` 写于项目最初，实验数量按纯算法项目设计（7 组），
> 而团队三人均为 0 基础、且这是《软件工程》课，故本文把实验裁到 3 组核心 + 1 组合并。

---

## 0. 项目定位（一句话，决定后面所有取舍）

> 做一个**手机拍照 → 服务端推理 → 返回 Top-3 病害候选 + 置信度**的辅助初筛工具，
> 并用实验证明"在叶片病害任务上，轻量 CNN 比大模型更适合部署"。

三个必须记住的判断，答辩会问：

1. **PlantVillage 上 99% 不可信** —— 实验室摆拍、单一背景、单叶，模型学到的是背景不是病斑。
2. **结论是轻量模型更合适** —— 参数量约 1/8，精度不差，手机/服务器跑得动。
3. **系统链路** —— 拍照 → 上传 → 预处理 → 推理 → softmax → Top-3 + 置信度 → 显示。

**明确的非目标**（写下来是为了防止范围蔓延）：
- 不做端侧推理（改为服务端，理由见第 2 节）
- 不做多叶片检测/分割（只做单叶分类）
- 不做"诊断"，App 内必须有免责声明
- 不做账号体系、不做社交功能

## 1. 系统最终形态

```
┌─────────────┐   HTTPS POST /predict    ┌──────────────────┐
│  安卓 App   │  (multipart, 一张 jpg)   │  FastAPI 服务    │
│  Kotlin     │ ───────────────────────► │  Python          │
│  Compose    │ ◄─────────────────────── │  ONNX Runtime    │
│             │  JSON: top3+confidence   │  SQLite          │
└─────────────┘                          └──────────────────┘
       │                                          │
       │ 用户点"结果不对"                          │ 存 predictions
       └──── POST /feedback ─────────────────────►│ 存 feedback
```

数据表最小设计（三张表就够）：

| 表 | 关键字段 | 用途 |
|---|---|---|
| `predictions` | id, created_at, image_path, top1, top1_prob, top3_json, latency_ms | 每次预测留痕 |
| `feedback` | id, prediction_id, is_correct, true_label, comment, created_at | 用户纠错 |
| `users` | id, device_id, created_at | 统计"用户数量"（课程硬要求） |

`request_id` / `prediction_id` 把预测和反馈关联起来 —— 这是整个系统里最重要的一行设计，
因为它让"模型错在哪"变成可查询的数据，而不是靠猜。

## 2. 关键技术决定（已定，不再讨论）

| 决定 | 选择 | 理由 |
|---|---|---|
| 推理位置 | **服务端** | 端侧要处理 ONNX Mobile 算子兼容、量化损失、芯片适配，0 基础团队大概率卡死；服务端 App 只发 HTTP 请求 |
| 后端框架 | **FastAPI** | 本机已装，自带 OpenAPI 文档页，前端联调方便 |
| 推理引擎 | **ONNX Runtime** | 本机已装；不依赖 torch，服务器部署体积小 |
| 数据库 | **SQLite** | 单文件，不用装服务，够用 |
| 安卓 | **Kotlin + Jetpack Compose** | 现代写法，代码量少，AI 生成质量高 |
| 安卓网络 | **Retrofit + OkHttp** | 事实标准，例子多 |
| 部署 | 先本机局域网，最后上 124.222.157.62 | 演示时手机连同一热点即可 |

**为什么不端侧**（这条要能讲）：模型能热更新、服务器算力不受手机限制、能集中收集反馈数据，
且"部署成本"本身就是我们要研究的对象之一 —— 把推理放服务端，反而让"轻量模型"的结论
从"能不能跑"变成"服务器成本差多少"，更可量化。

### S3 · E1 模型结构对比（主线实验，1-2 天）

**分两批跑，先跑三个够写结论，有余力再补。**

| 批次 | 模型 | 代表 |
|---|---|---|
| 第一批（必跑） | resnet18 / mobilenet_v3_large / swin_t | 标准 CNN / 轻量 CNN / Transformer |
| 第二批（有余力） | resnet50 / shufflenet_v2_x1_0 / efficientnet_b0 | 大容量 / 更轻 / 复合缩放 |

| 项 | 内容 |
|---|---|
| 产物 | `report/figures/acc_vs_params.png`（散点图，横轴参数量、纵轴精度）；对比表（精度 / macro-F1 / 参数量 / 训练时长） |
| 验收 | 能回答"MobileNetV3 参数量是 ResNet50 的几分之一、精度差多少" |
| 学什么 | 第二层：六个模型分别回答什么问题（见 `docs/讲解/六模型对比.md`，待写） |

**预期结论**（实验后验证或推翻，不预设）：
三个模型 test acc 差距应在 1% 以内；MobileNetV3 参数量约为 ResNet50 的 1/8；
Swin-T 参数量最大但精度不一定最高 —— 这正好支撑"容量不是瓶颈，部署成本才是"。

### S4 · E2 跨域 + E3 效率 + E7 热力图（差异化亮点，2-3 天）

这是整个项目**最有价值**的一步，也是最能和其他组拉开差距的地方。

| 子任务 | 内容 | 坑 |
|---|---|---|
| S4.1 下载 PlantDoc | HuggingFace `LamTNguyen/PlantDoc`，939MB | 它是**目标检测**格式（带 bbox），不是纯分类 |
| S4.2 类别映射 | PlantDoc 的类名和 PlantVillage 不一致，需要手工建映射表 | **这是本项目最大的数据坑**，见下 |
| S4.3 跨域测试 | 用 S2/S3 的模型在映射后的子集上测 | 只保留能映射上的类，其余丢弃并记录丢弃量 |
| S4.4 效率实测 | 参数量、FLOPs（用 `torchprofile` 或手算）、CPU 单张延迟（本机 Ryzen 测）、ONNX 模型体积 | 参数量小 ≠ 延迟低，要实测 |
| S4.5 Grad-CAM | 同域 vs 跨域各画 8 张热力图，对比模型看哪里 | 需要 `pytorch-grad-cam` 或手写 20 行 |

| 项 | 内容 |
|---|---|
| 产物 | `report/figures/cross_domain_drop.png`（同域 vs 跨域柱状图）；`gradcam_compare.png`；效率表 |
| 验收 | 能回答"精度掉了多少、为什么掉、热力图证明了什么" |
| 学什么 | 第三层：混淆矩阵怎么读；域偏移是什么 |

**类别映射的诚实做法**：PlantDoc 只有 13 种作物、27 类（含健康），
和 PlantVillage 的 38 类只有部分交集。不要硬凑 —— 建一张映射表，
只保留能确定的类，明确写出"映射后保留 N 类、M 张图，丢弃 X 张"。
这比假装全部对齐可信得多，老师也会认可这种严谨。

**预期**：跨域精度掉到 30%-60%。如果没掉这么多，反而要怀疑是不是数据泄漏了
（比如 PlantDoc 里有和 PlantVillage 重复的图）。
