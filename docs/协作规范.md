# 协作规范

> 三个人都是第一次协作开发，这份文档的目的是**避免互相覆盖代码**。规矩越少越好记，但下面这几条不能破。

## 一、分支模型

只有两个长期分支：

| 分支 | 用途 | 谁能直接推 |
|---|---|---|
| `main` | 随时可运行、可演示的版本 | **谁都不能**（见下） |
| `dev` | 日常集成分支 | 谁都不能 |

干活时从 `dev` 拉自己的分支：

```bash
git checkout dev
git pull
git checkout -b feat/你的名字-做什么
```

分支命名举例：
- `feat/wky-train-script` — 王楷宇写训练脚本
- `feat/backend-api` — 后端做接口
- `fix/app-camera-crash` — 修安卓相机崩溃

**为什么 `main` 不能直接推**：`main` 是最后要交给老师、要演示的版本。任何一次手滑推错，整个项目就废了。GitHub 上已经设了保护，推不上去不是你操作错了。

## 二、提交信息怎么写

格式：`类型: 做了什么`

```
feat: 增加六模型训练脚本
fix: 修正类别映射导致的标签错位
docs: 补充数据体检结论
refactor: 把数据增强抽成独立函数
chore: 更新依赖版本
```

**禁止的提交信息**：`update`、`修改`、`1`、`asdf`、`.`、`再改一下`

为什么较真：两周后你看到 `git log` 里 30 条 `update`，你不知道哪次改坏了。课程报告里也要写迭代过程，提交记录就是证据。

## 三、每天开工前

```bash
git checkout dev
git pull
```

**不 pull 就开始写，是冲突的头号来源。**

## 四、提交前必须做的检查

```bash
git status
```

确认三件事：

1. **没有 `ml/data/` 下的文件**（2.37GB，推不上去还会卡死仓库）
2. **没有 `*.pt` / `*.onnx` 权重文件**
3. **没有 `.env` 之类含密码的文件**

`.gitignore` 已经配好了，但 `git add -A` 之前扫一眼不费事。真推上去了很难彻底删掉（Git 历史里会留痕）。

## 五、合并流程

1. 推自己的分支：`git push -u origin feat/xxx`
2. 在 GitHub 上开 Pull Request，目标选 `dev`
3. **至少一个人看过才能合并**——哪怕只看一眼"改了哪些文件"
4. 合并后删掉自己的分支

零基础阶段 PR 不用写长篇描述，但要说清一句：**这个 PR 让什么从"不能跑"变成"能跑"**。

## 六、冲突了怎么办

```bash
git checkout dev
git pull
git checkout feat/你的分支
git merge dev
```

然后在编辑器里解决冲突（`<<<<<<<` 到 `>>>>>>>` 之间的内容）。

**解决不了就停下来问，不要凭感觉删。** 冲突标记删错会导致代码语法错误，而且很难事后发现。

## 七、绝对不要做的事

| 操作 | 后果 |
|---|---|
| `git push --force` | 会覆盖别人的提交，且无法恢复 |
| `git reset --hard` 在有未提交改动时 | 你的改动直接消失 |
| 提交 `ml/data/` | 仓库体积暴涨，可能永久污染历史 |
| 把 token/密码写进代码再提交 | 公开仓库=全世界可见，必须立刻作废重发 |
| 直接改别人正在写的文件 | 必然冲突，先沟通 |

## 八、出问题了先别慌

代码推坏了、改乱了，**先停手，把 `git status` 和报错贴到群里**。

只要没有 `--force` 过，Git 里的东西基本都能找回来。慌着乱敲命令才是真正会丢东西的时候。
