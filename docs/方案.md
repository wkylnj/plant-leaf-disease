# 植物叶片病害图像识别分析系统 —— 项目方案

> 课程：《软件工程原理与实践》
> 大作业性质：神经网络相关的软件系统，需满足敏捷两轮迭代 + 真实用户 + gitee 公开
> 团队：3 人
> 文档版本：v1（2026-11-17）

---

## 一、选题与定位

### 1.1 选题

**植物叶片病害图像识别分析系统**：用户用手机拍一张作物叶片，App 返回病害名称、置信度和防治建议。

### 1.2 这门课的评分实际有两条轴

课程名是软件工程，但大作业内容是神经网络。这意味着评分不会只看模型精度，也不会只看代码量，而是两条轴都要立住：

| 轴 | 评分关注点 | 本方案的对应设计 |
|---|---|---|
| 软件工程 | 需求分析是否真实、两轮迭代是否落地、文档是否完整、有没有真实用户和反馈、反思是否诚恳 | 完整的需求/设计/迭代文档 + 真实 APK 分发 + App 内反馈收集 + 两轮反思 |
| 神经网络 | 实验设计是否合理、对比是否公平、分析是否有深度、有没有超出"跑通一个模型" | 6 模型横向对比 + 跨域泛化测试 + 效率实测 + Grad-CAM 可解释性 + 消融 |

只做前者，报告会变成一份产品说明书；只做后者，就交不出"可用软件"。方案的核心是让两者互相支撑：**软件工程提供了真实场景和真实数据，神经网络实验提供了系统的技术内核。**

### 1.3 一个必须提前想清楚的问题：PlantVillage 已经被刷爆了

PlantVillage 上 ResNet 类模型轻松做到 99%+，这是公开数据集里的常识。如果报告结论是"我们的模型准确率 99.2%"，老师第一个问题就是"那又怎样"。

所以本项目的技术叙事不能是"刷精度"，而必须是**回答一个具体问题**：

> **在植物叶片病害识别任务上，模型结构与容量如何影响「同域精度」「跨域鲁棒性」「部署成本」这三个互相冲突的目标？对手机端应用而言，什么才是理性选择？**

这个问题有确定的、可测量的答案，而且答案大概率反直觉（见 3.4 的预期结论），报告才有东西可写。

## 二、需求分析

### 2.1 用户画像

| 角色 | 特征 | 核心诉求 | 对设计的约束 |
|---|---|---|---|
| 主要用户：种植户 / 农技推广员 | 有智能手机，网络条件一般，非技术用户 | 拍一下就知道是什么病、怎么治 | 界面极简、大按钮、结果要给出可执行的防治建议而不只是病名 |
| 次要用户：农业院校学生 / 爱好者 | 会用 App，愿意反馈 | 想看到模型判断依据、想纠正错误 | 提供 top-3 候选和置信度，提供纠错入口 |
| 团队自身：开发者 | 需要评估模型真实表现 | 收集真实场景图片和用户标注 | App 内埋点，把用户反馈变成后续迭代的数据 |

### 2.2 功能需求（MoSCoW 分级）

**Must have（Alpha 必须完成）**
- F1 拍照识别：调用相机拍摄或从相册选择图片
- F2 上传推理：图片上传服务端，返回识别结果
- F3 结果展示：Top-3 病害名称 + 置信度 + 防治建议文本
- F4 识别历史：本地保存历史记录，可回看

**Should have（Beta 完成）**
- F5 用户纠错：结果页提供"识别不对"入口，提交真实标签
- F6 置信度预警：低置信度时提示"建议咨询农技人员"，避免误导
- F7 模型信息页：展示当前模型版本、准确率、适用作物范围

**Could have（有余力再做）**
- F8 离线降级：无网络时用端侧小模型兜底
- F9 病害知识库：常见病害图文说明
- F10 批量识别：一次选多张图

**Won't have（明确不做，写进报告说明理由）**
- 用户注册登录体系（增加使用门槛，与"降低真实用户获取成本"冲突）
- 病害严重程度分级（需要分割标注，数据不具备）
- 多语言（目标用户为中文用户）

### 2.3 非功能需求

| 类别 | 指标 | 说明 |
|---|---|---|
| 性能 | 单张图端到端响应 < 3s（4G 网络） | 超过 3s 用户会以为卡死 |
| 性能 | 服务端单张推理 < 500ms | CPU 部署下的目标 |
| 可用性 | 服务可用率 ≥ 95%（迭代期内） | 学生项目服务器，不做 SLA 承诺 |
| 兼容性 | Android 8.0 (API 26) 及以上 | 覆盖绝大多数在用设备 |
| 体积 | APK < 30MB | 走服务端推理，模型不打进包 |
| 隐私 | 图片仅用于推理，不长期留存原图 | 报告里需说明数据合规态度 |

### 2.4 关键用例

```
用例：拍照识别病害
  参与者：种植户
  前置：已安装 App，有网络
  主流程：
    1. 用户点击"拍照识别"
    2. 系统调起相机，用户拍摄叶片
    3. 系统压缩图片并上传
    4. 服务端返回 Top-3 结果
    5. 系统展示病害名称、置信度、防治建议
  异常流程：
    3a. 网络失败 → 提示重试，图片暂存本地
    4a. 服务端超时 → 提示稍后重试，记录日志
    4b. 置信度 < 阈值 → 展示"无法确定"，建议咨询农技人员
```

## 三、神经网络部分设计（技术核心）

### 3.1 数据集

| 数据集 | 用途 | 规模 | 特点 |
|---|---|---|---|
| PlantVillage | 训练 + 同域测试 | 54,381 张 / 38 类 | 实验室条件，单叶片居中，背景干净 |
| PlantDoc | 跨域测试（只评估，不训练） | ~2,600 张 / 27 类（与 PV 取交集） | 真实田间拍摄，多叶片、复杂背景、光照不均 |

**类别不均衡是真实存在的**：PlantVillage 最少类 122 张（Orange 黄龙病），最多类 4,406 张，相差 36 倍。这直接决定评估指标不能只看 accuracy，必须同时报 macro-F1 和每类召回率。

**切分**：train 39,170 / val 4,333 / test 10,878，分层抽样，固定随机种子 42，保证可复现。

### 3.2 实验矩阵

设计原则：每个实验回答一个问题，不做无目的的堆砌。

| 编号 | 实验 | 变量 | 回答什么问题 |
|---|---|---|---|
| E1 | 模型结构对比 | ResNet18 / ResNet50 / MobileNetV3-L / ShuffleNetV2-x1.0 / EfficientNet-B0 / Swin-T | 同域精度与模型容量、归纳偏置的关系 |
| E2 | 跨域泛化 | 上述 6 个模型在 PlantDoc 上直接测试 | 实验室精度能迁移多少到真实场景 |
| E3 | 效率实测 | 参数量 / FLOPs / 服务端 CPU 延迟 / 手机端延迟 | 精度的代价是多少 |
| E4 | 输入分辨率 | 224 vs 320（ResNet50、MobileNetV3-L） | 病害是细粒度纹理，分辨率是否是瓶颈 |
| E5 | 增强强度消融 | 强增强 vs 弱增强（ResNet18） | 强增强对同域/跨域的影响是否一致 |
| E6 | 类别平衡消融 | WeightedRandomSampler 开/关（ResNet18） | 不均衡对 macro-F1 的实际影响 |
| E7 | 可解释性 | Grad-CAM（同域图 vs 跨域图） | 模型到底在看病斑还是看背景 |

**规模控制**：E1/E2 是主线，6 个模型各训 1 次；E4–E6 是补充实验，只跑 1–2 个模型。不做 5 折交叉验证（Colab 算力不允许），改为对前 2 名模型跑 3 个随机种子报均值±标准差，用最小代价说明结果不是偶然。

### 3.3 评估指标

| 指标 | 为什么需要 |
|---|---|
| Top-1 Accuracy | 最直观，但会被大类主导 |
| Macro-F1 | 每类等权，暴露小类别上的失败 |
| 每类召回率 | 找出"哪些病害根本识别不出来" |
| 混淆矩阵 | 看错误集中在哪些类别对（如 Tomato 早疫 vs 晚疫） |
| ECE（期望校准误差） | 置信度是否可信——直接关系到 F6 的置信度预警能不能做 |
| 参数量 / FLOPs | 效率维度 |
| 端到端延迟 | 真实体验 |

### 3.4 预期结论（写方案时就要敢下判断，实验后验证或推翻）

1. **同域精度会饱和**：6 个模型在 PlantVillage 测试集上大概率都落在 97%–99.5%，差距在统计上不显著。这本身就是一个结论：**在这个数据集上比精度没有意义**。
2. **跨域会崩塌**：PlantDoc 上准确率预计掉到 30%–60%。崩塌幅度比同域精度差异重要得多。
3. **轻量模型不吃亏**：MobileNetV3 / ShuffleNet 以约 1/10 的算力达到与 ResNet50 相当的同域精度，是移动端部署的理性选择。
4. **模型看的是背景**：Grad-CAM 预计显示同域图上注意力集中在叶片病斑，跨域图上注意力分散到背景、土壤、其他叶片。这解释了第 2 条，也是全篇最有说服力的分析。

> 如果实验结果与预期不符，报告要如实写，并分析原因。**"预期被推翻"比"预期被验证"更有价值**，这一点会在报告中明确说明。

### 3.5 可选的改进尝试（Beta 阶段，视进度决定）

针对"模型学背景"这个问题做一次最小改进尝试：训练时随机替换背景（用纯色或其他图片填充叶片外区域），看跨域精度是否提升。成功则报告"改进有效"，失败则报告"简单背景扰动不足以解决域偏移"——两种结果都能写。

## 四、系统架构

### 4.1 总体架构

```
┌─────────────────┐      HTTPS/JSON      ┌──────────────────┐
│  Android App    │ ───────────────────► │  FastAPI 服务端   │
│  (Kotlin +      │ ◄─────────────────── │  (Python)        │
│   Jetpack       │    Top-3 + 建议       │                  │
│   Compose)      │                      │  ┌────────────┐  │
└─────────────────┘                      │  │ ONNX Runtime│ │
                                         │  │  模型推理   │ │
┌─────────────────┐                      │  └────────────┘  │
│  H5 分享页      │ ───────────────────► │                  │
│  (可选，Beta)   │                      │  ┌────────────┐  │
└─────────────────┘                      │  │ SQLite      │  │
                                         │  │ 反馈/日志   │  │
                                         │  └────────────┘  │
                                         └──────────────────┘
```

**为什么走服务端推理而不是端侧**：
- 模型可以随时更新，不用让用户重装 APK
- 手机 CPU 跑 ViT 级模型延迟不可接受，而服务端可以选任意模型
- 能集中收集用户反馈数据，这对"展示用户反馈"的要求是刚需
- 代价是必须联网——通过 F6/F8 缓解

### 4.2 模块划分

| 模块 | 职责 | 技术选型 | 负责人 |
|---|---|---|---|
| 训练管线 | 数据预处理、训练、评估、导出 | PyTorch + torchvision | A |
| 模型服务 | 加载 ONNX、推理、返回 Top-3 | FastAPI + onnxruntime | B |
| 业务接口 | 上传、历史、反馈、健康检查 | FastAPI + SQLite | B |
| 安卓客户端 | 拍照、上传、结果展示、历史、反馈 | Kotlin + Compose + Retrofit | C |
| 部署运维 | 服务器环境、反向代理、日志 | Docker / systemd + Nginx | B |

### 4.3 接口设计（草案）

```
POST /api/v1/predict
  Content-Type: multipart/form-data
  Body: image=<file>
  Response 200:
    {
      "request_id": "uuid",
      "topk": [
        {"label": "Tomato___Late_blight", "name_zh": "番茄晚疫病", "prob": 0.923},
        {"label": "Tomato___Early_blight", "name_zh": "番茄早疫病", "prob": 0.051},
        ...
      ],
      "low_confidence": false,
      "advice": "……防治建议文本……",
      "model_version": "resnet50-v1"
    }

POST /api/v1/feedback
  Body: {"request_id": "...", "predicted": "...", "corrected": "...", "comment": "..."}

GET /api/v1/health   → {"status": "ok", "model_version": "..."}
```

`request_id` 是关键设计：把预测和反馈关联起来，才能统计"用户说错了多少次、错在哪"。

### 4.4 安卓端页面

| 页面 | 内容 | 设计要点 |
|---|---|---|
| 首页 | 大按钮"拍照识别" + "从相册选择" + 最近记录入口 | 一屏放下，无滚动，目标用户不需要学习 |
| 结果页 | 大图 + 病害名 + 置信度条 + Top-3 列表 + 防治建议 + "识别不对"按钮 | 置信度用颜色区分（高绿/中黄/低红） |
| 历史页 | 时间倒序的识别记录列表 | 本地存储，可删除 |
| 关于页 | 模型版本、准确率、适用作物、隐私说明 | 满足透明性要求 |

## 六、迭代计划

课程规定的时间结构是 1–7 周准备、8–12 周 Alpha、13–15 周 Beta、16 周总结。以下按这个结构排，具体日期待确认当前周次后填入。

### 6.1 Alpha 迭代（4 周）——目标：跑通端到端

| 周 | 目标 | 验收标准（可演示） |
|---|---|---|
| A1 | 数据管线 + 基线模型 | ResNet18 在 PlantVillage 上训练完成，测试集准确率 > 95% |
| A2 | 服务端最小可用 | `curl` 上传一张图能返回 Top-3 JSON |
| A3 | App 最小可用 | 手机上拍照 → 上传 → 看到结果（界面可以丑） |
| A4 | 联调 + 首次分发 | 发出第一个 APK 给 3–5 个真实用户试用，收集第一轮反馈 |

**Alpha 评审要点**：端到端是否真的通了？真实用户能不能独立完成一次识别？

### 6.2 Beta 迭代（3 周）——目标：从"能跑"到"好用"

| 周 | 目标 | 验收标准 |
|---|---|---|
| B1 | 修 Alpha 的 bug + 补 E1/E2 完整实验 | 6 模型对比表完成，跨域测试完成 |
| B2 | 功能补全（F5 反馈、F6 预警、F7 模型信息）+ 界面优化 | 反馈数据能入库并统计 |
| B3 | 扩大用户范围 + 压力测试 + 报告主体 | 用户数 ≥ 20，反馈条数 ≥ 50，报告初稿完成 |

### 6.3 总结（1 周）

报告定稿、演示准备、gitee 材料整理。

## 九、风险与应对

| 风险 | 影响 | 应对 |

## 十一、方案的自我评估

**这个方案强在哪**

- 技术上有明确的问题意识，不是"跑通一个模型"，而是回答一个可证伪的问题，并且预期结论本身就有反直觉性（同域精度无差异、跨域崩塌、轻量模型不吃亏）。
- 软件工程的要求和神经网络的内容是咬合的：App 是模型的真实使用场景，用户反馈是后续迭代的数据来源，不是两张皮。
- 风险控制务实：模型数量、实验规模、迭代节奏都按 3 人 8 周的实际能力裁剪过，没有画大饼。

**这个方案弱在哪（需要提前承认）**

- 跨域实验依赖 PlantDoc 的类别映射质量，如果映射覆盖率低，E2 的说服力会打折。
- 端到端延迟的实测数据受服务器和网络条件限制，不能代表生产环境。
- 真实用户规模大概率在几十人量级，统计意义上说明不了太多问题，报告里要如实定位为"可用性验证"而非"效果验证"。
- 6 个模型的完整训练在免费 Colab 上有时间风险，可能需要砍到 4–5 个。
